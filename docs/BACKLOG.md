# BACKLOG — идеи из анализа проекта, в работу пока не берутся

Здесь лежат пункты, которые не вошли в текущую итерацию. Порядок примерно по
убыванию ценности. Перед взятием в работу — обсудить и, если нужно, внести в
`docs/SPEC.md` явным решением владельца.

## Улучшения CLI

1. **Подсказка `--help` при ошибках использования (код 2).** Сейчас печатается
   только строка ошибки с префиксом `krot:`; добавить `see --help` или краткий
   синтаксис действия. Точка входа: `App.Run` (`internal/app/app.go`).

2. **Shell completion и man-страница.** Для 10 действий и ~17 флагов completion
   заметно ускоряет работу. Варианты: скрытая команда `krot --completion bash|zsh`
   или заранее сгенерированные файлы в пакетах (nfpm `contents`).

## Поведение

3. **TOCTOU в `--delete`.** Подтверждение спрашивается до взятия блокировки
   (осознанно, см. комментарий в `internal/app/tunnel.go`): клиент, добавленный
   между вопросом и lock, будет удалён без повторного подтверждения. Варианты:
   переспросить после взятия блокировки, если состав клиентов изменился, либо
   задокументировать поведение в README.

4. **`--list` без установленных инструментов.** Сейчас `need()` требует
   `wg`/`awg` даже для показа лежачих конфигов (`internal/app/list.go`).
   По SPEC 2.2 это допустимо, но на минимальной системе листинг конфигов был бы
   полезен (со статусом `down` без проверки). Требует решения по ТЗ: деградация
   статуса или сохранение ошибки 6.

## Инструменты качества

5. **staticcheck в CI.** В анализе не вошёл: локально не удалось проверить
   работу свежего staticcheck против Go 1.27 (export data v5, релиз 2025.1
   не совместим). Добавить, когда проверяемо; запуск:
   `go run honnef.co/go/tools/cmd/staticcheck@<версия> ./...`.

6. **gosec.** Статический анализ безопасности (файловые права, exec, crypto).
   Проверить локально перед включением в CI, чтобы не получить красный пайплайн
   от ложных срабатываний.

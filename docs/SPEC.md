## 1. Назначение

`krot` — консольная утилита на Go для управления туннелями WireGuard и AmneziaWG
на Linux-серверах: создание и удаление интерфейсов, управление клиентами (peer'ами),
выдача клиентских конфигов и QR-кодов.

Принципы:
- простота: один статический бинарь, минимум зависимостей;
- операции с клиентами **никогда** не перезапускают и не сбрасывают интерфейс;
- предсказуемый вывод для людей (таблицы) и для автоматизации (`--json`, коды выхода);
- krot не управляет NAT, forwarding и firewall — это за пределами утилиты.

## 2. Окружение и зависимости

### 2.1. Целевые ОС

| Семейство | Версии | Пакет |
|---|---|---|
| Ubuntu | 22.04, 24.04, 26.04 | `.deb` |
| Debian | 12, 13 | `.deb` |
| AlmaLinux | 9, 10 (совместимо с Rocky/RHEL) | `.rpm` |

Архитектуры: `amd64`, `arm64`.

### 2.2. Внешние программы (krot их не устанавливает)

| Тип | Требуется |
|---|---|
| `wg` | `wireguard-tools` (`wg`, `wg-quick`), модуль ядра WireGuard |
| `awg`, `awg2`, `awg3` | `amneziawg-tools` (`awg`, `awg-quick`), модуль ядра AmneziaWG **или** `amneziawg-go` |
| все | `ip` (iproute2), `systemd` |

Если нужной программы нет — ошибка с кодом `6` и понятным текстом, какой пакет нужен.

### 2.3. Go-зависимости

- Стандартная библиотека Go (`flag`, `text/tabwriter`, `encoding/json`, `crypto/*`, `net/netip`).
- Одна внешняя библиотека для генерации QR-кода. Любая другая новая зависимость — только с одобрения владельца.
- Ключи Curve25519 генерируются средствами Go (`golang.org/x/crypto/curve25519` допустим как часть x/crypto), без вызова `wg genkey`.
- Сборка: `CGO_ENABLED=0`, статический бинарь.

### 2.4. Права

Все действия, кроме `--help` и `--version`, требуют root. Без root — код `6`.

## 3. Типы протоколов

| `--type` | Протокол | Конфиги | systemd unit | Утилита |
|---|---|---|---|---|
| `wg` | WireGuard | `/etc/wireguard/<if>.conf` | `wg-quick@<if>` | `wg` |
| `awg` | AmneziaWG 1.x (1.0; 1.5 при заданном `--i1`) | `/etc/amnezia/amneziawg/<if>.conf` | `awg-quick@<if>` | `awg` |
| `awg2` | AmneziaWG 2.0 | `/etc/amnezia/amneziawg/<if>.conf` | `awg-quick@<if>` | `awg` |
| `awg3` | AmneziaWG 3.1 | `/etc/amnezia/amneziawg/<if>.conf` | `awg-quick@<if>` | `awg` |

### 3.1. Проверка установленной версии AmneziaWG

Тип задаётся явно через `--type`. Перед `--create` krot проверяет, что установленная
AmneziaWG поддерживает запрошенный тип:

1. версия утилит: `awg --version`;
2. версия модуля: `/sys/module/amneziawg/version`, если модуль загружен; иначе `modinfo amneziawg`;
3. если модуля нет — наличие `amneziawg-go` в `PATH` и его версия.

Если установленная версия ниже требуемой — ошибка `6`:
`awg3 requires AmneziaWG >= 3.1, installed: 2.0.x`.

Таблица «тип → минимальная версия tools / модуля / amneziawg-go» заполняется в задаче **T0**
по реальным релизам и выводу команд. До её заполнения проверка идёт по мажорной версии.
Таблица хранится в коде в одном месте и покрывается тестами на реальных примерах вывода
(golden-файлы в `testdata/`).

### 3.2. Определение версии существующего интерфейса (для `--list`)

Если в конфиге есть метаданные krot (`# krot:type=...`) — используются они.
Иначе версия определяется по параметрам `[Interface]`:

| Признак | Версия |
|---|---|
| есть `HeaderProtectionKey`, `RandomTrailers` или `DisableCookies` | 3.1 |
| есть `HeaderProtectionKey` без ключей 3.1 | 3.0 |
| есть `S3`/`S4` или H1–H4 заданы диапазоном | 2.0 |
| есть `I1`–`I5`, нет `S3`/`S4` | 1.5 |
| есть `Jc`/`S1`/`H1` | 1.0 |
| AWG-параметров нет | `wg` (для конфига в каталоге amnezia — `awg (compat)`) |

## 4. Интерфейс командной строки

### 4.1. Общие правила

- Ровно одно действие за запуск. Ноль или два действия — ошибка `2`.
- Флаги только в длинной форме `--flag value` или `--flag=value`.
- Флаг, не применимый к выбранному действию, — ошибка `2` (не игнорируется молча).
- Обычный вывод — в stdout, ошибки и предупреждения — в stderr.
- `--help` выводит справку; `--version` — версию, коммит и дату сборки.

### 4.4. Описание параметров

| Параметр | Формат | Описание |

| `--psk` | флаг | сгенерировать PresharedKey для клиента |
| `--qr` | флаг | дополнительно вывести клиентский конфиг QR-кодом |
| `--json` | флаг | вывод в JSON вместо таблицы |
| `--yes` | флаг | не спрашивать подтверждение |

### 4.5. Коды выхода

| Код | Значение |
|---|---|
| 0 | успех |
| 1 | внутренняя или неожиданная ошибка |
| 2 | ошибка использования CLI (флаги) |
| 3 | ошибка валидации значений |
| 4 | объект не найден (интерфейс, клиент) |
| 5 | конфликт (уже существует, адрес или порт занят) |
| 6 | окружение (нет root, нет утилит, неподходящая версия AmneziaWG) |
| 7 | не удалось получить блокировку |

## 5. Хранение данных

### 5.1. Конфиг — единственный источник правды

krot не ведёт отдельной базы. Все данные хранятся в конфигах интерфейсов в виде
комментариев-метаданных, которые `wg-quick`/`awg-quick` игнорируют.

Пример `/etc/amnezia/amneziawg/awg0.conf`:

```ini
# krot:type=awg2
# krot:endpoint=vpn.example.com
# krot:dns=1.1.1.1,9.9.9.9
[Interface]
PrivateKey = ...
Address = 10.8.0.1/24, fd00:8::1/64
ListenPort = 51820
MTU = 1376
Jc = 6
Jmin = 64
Jmax = 512
S1 = 43
S2 = 117
S3 = 31
S4 = 12
H1 = 194847201-195371488
H2 = 905128442-905652729
H3 = 1503002211-1503526498
H4 = 2001009901-2001534188
# PreUp =
# PostUp =
# PreDown =
# PostDown =

# krot:id=phone-sergei
# krot:created=2026-10-17T01:30:00Z
[Peer]
PublicKey = ...
PresharedKey = ...
AllowedIPs = 10.8.0.2/32, fd00:8::2/128

# krot:id=laptop-old
# krot:created=2026-10-01T10:00:00Z
# krot:locked=2026-10-16T12:00:00Z
#~ [Peer]
#~ PublicKey = ...
#~ AllowedIPs = 10.8.0.3/32
```

Правила:
- Метаданные интерфейса — строки `# krot:<ключ>=<значение>` перед `[Interface]`.
- Метаданные клиента — строки `# krot:...` непосредственно перед его `[Peer]`.
- Заблокированный клиент: каждая строка его блока `[Peer]` закомментирована префиксом `#~ `, добавлен `# krot:locked=<время>`.
- Закомментированные `PreUp`/`PostUp`/`PreDown`/`PostDown` добавляются при `--create` всегда, без значений.
- Права на файл — `0600`, владелец `root:root`.

### 5.2. Приватные ключи клиентов

Не хранятся нигде. Клиентский конфиг и QR показываются **один раз** — при `--add-client`.
На сервере хранятся только `PublicKey` и (если есть) `PresharedKey` клиента.

### 5.3. Чужие конфиги

krot обязан корректно читать конфиги, созданные не им (без метаданных):
- `--list` их показывает;
- `--list-client` показывает peer'ов без `krot:id` с id `-`;
- клиентские операции по `--id` к таким peer'ам неприменимы;
- при любой записи все чужие строки, комментарии и порядок сохраняются без изменений.

### 5.4. Атомарная запись

Любое изменение конфига: запись во временный файл в том же каталоге (`0600`) → `fsync` →
`rename` поверх оригинала → `fsync` каталога. Частично записанный конфиг невозможен.

### 5.5. Блокировка

Каждое изменяющее действие берёт эксклюзивный `flock` на `/run/lock/krot.lock`
с ожиданием до 10 секунд. Не удалось получить — код `7`.
Причина: защита от гонок «прочитал → изменил → записал» при параллельных запусках
(например, Salt и человек одновременно).

## 6. Поведение действий

### 6.1. `--list`

Таблица (`text/tabwriter`), отсортированная по имени интерфейса:

```
INTERFACE  TYPE  VERSION  ADDRESS                    PORT   STATUS  CLIENTS
awg0       awg2  2.0      10.8.0.1/24,fd00:8::1/64   51820  up      12 (1 locked)
wg0        wg    -        10.9.0.1/24                51821  down    3
```

- Источник — конфиги из обоих каталогов плюс состояние живых интерфейсов (`wg show` / `awg show`).
- `STATUS`: `up` — интерфейс существует в системе; `down` — есть только конфиг.
- `VERSION` — только для AmneziaWG (раздел 3.2), для `wg` — `-`.
- Фильтры `--type`, `--interface`, `--ip`, `--port` объединяются по И.
- `--json` выдаёт массив объектов с полями: `interface`, `type`, `version`, `addresses[]`, `port`, `status`, `clients_total`, `clients_locked`.
- Пустой результат — пустая таблица (только заголовок) или `[]`, код `0`.

### 6.2. `--create`

1. Проверить флаги и окружение (root, утилиты, версия AmneziaWG — раздел 3.1).
2. Если `--interface` не задан — взять первое свободное имя: `wg0, wg1…` для `wg`, `awg0, awg1…` для `awg*`.
3. Проверить конфликты (код `5`): существует конфиг или интерфейс с таким именем; порт занят другим конфигом krot или слушается в системе.
4. Сгенерировать ключ сервера и параметры обфускации (раздел 7).
5. Записать конфиг атомарно.
6. `systemctl enable --now <unit>@<if>`.
7. Вывести краткую сводку: имя, тип, адреса, порт, endpoint.

При ошибке на шаге 6 конфиг удаляется, unit отключается — система возвращается в исходное состояние.

IPv6 добавляется только если в `--ip` явно передан IPv6-адрес.

### 6.3. `--delete`

1. Интерфейс должен существовать (код `4`).
2. Если в конфиге есть клиенты (включая заблокированных) — предупреждение
   `Interface awg0 has 12 clients. Delete? [y/N]`.
   - `--yes` — подтверждение без вопроса.
   - stdin не TTY и нет `--yes` — ошибка `2` без удаления.
   - ответ не `y`/`yes` — код `10`.
3. `systemctl disable --now <unit>@<if>`, удалить конфиг.

Бэкап не делается.

### 6.4. `--up` / `--down`

`systemctl start|stop <unit>@<if>`. Тип определяется по расположению и содержимому конфига.
Повторный `--up` на поднятом интерфейсе — код `0` с сообщением «already up» (идемпотентно).

### 6.5. `--add-client`

1. Интерфейс существует (код `4`), `--id` уникален в интерфейсе (код `5`, учитываются и заблокированные).
2. Адреса клиента:
   - если `--ip` задан — проверить, что адреса в подсетях интерфейса и свободны (иначе код `5`);
   - если не задан — выдать первый свободный IPv4 `/32` из подсети интерфейса; если у интерфейса есть IPv6 — также первый свободный IPv6 `/128`.
   - Не выдаются: адрес сети, broadcast (IPv4), адреса сервера, адреса любых клиентов (включая заблокированных).
   - Свободных адресов нет — код `5`.
3. Сгенерировать ключи клиента; при `--psk` — PresharedKey.
4. Записать peer в конфиг атомарно.
5. Если интерфейс поднят — применить вживую: `wg|awg set <if> peer <pub> allowed-ips <ips> [preshared-key <file>]`.
   PSK передаётся через временный файл `0600`, удаляемый сразу после вызова.
6. Если шаг 5 не удался — откатить конфиг к исходному состоянию, код `1`.
7. Вывести клиентский конфиг; при `--qr` — дополнительно QR-код в терминал (символы Unicode half-block).

Клиентский конфиг:

```ini
[Interface]
PrivateKey = <ключ клиента>
Address = 10.8.0.2/32, fd00:8::2/128
DNS = 1.1.1.1, 9.9.9.9          # если задан --dns при create
MTU = 1376
<все AWG-параметры интерфейса, включая I1, если задан>

[Peer]
PublicKey = <ключ сервера>
PresharedKey = <psk>             # если --psk
Endpoint = vpn.example.com:51820
AllowedIPs = <значение --allowed-ips>
PersistentKeepalive = 25
```

Если конфиг не помещается в QR-код (максимальная версия 40, уровень коррекции L) —
конфиг выводится текстом, затем ошибка `3` с текстом «config too large for QR».

### 6.6. `--delete-client`

Удалить peer из конфига атомарно; если интерфейс поднят и клиент не заблокирован —
`wg|awg set <if> peer <pub> remove`. Удаление заблокированного клиента допустимо.

### 6.7. `--lock-client`

Закомментировать блок peer (раздел 5.1) атомарно; если интерфейс поднят —
`wg|awg set <if> peer <pub> remove`. Повторная блокировка — код `0`, «already locked».

### 6.8. `--unlock-client`

Раскомментировать блок peer атомарно; если интерфейс поднят — добавить peer вживую
с его `AllowedIPs` и `PresharedKey`. Повторная разблокировка — код `0`, «already unlocked».

### 6.9. `--list-client`

```
ID            PUBLIC KEY     ADDRESS                     STATUS   LAST HANDSHAKE  RX       TX
phone-sergei  aB3d…Xy9=      10.8.0.2/32,fd00:8::2/128   active   1m ago          12.4MiB  1.1GiB
laptop-old    Qw7e…Zz1=      10.8.0.3/32                 locked   -               -        -
```

- Данные из конфига плюс `wg|awg show <if> dump` для поднятого интерфейса.
- Фильтр `--id`.
- `--json`: `id`, `public_key` (полный), `addresses[]`, `status`, `latest_handshake` (unix time или `null`), `rx_bytes`, `tx_bytes`, `endpoint` (или `null`), `created`.

### 6.10. Требование незаметности (ключевое)

Операции `--add-client`, `--delete-client`, `--lock-client`, `--unlock-client` **запрещено**
реализовывать через `wg-quick down/up`, `systemctl restart`, пересоздание интерфейса или
полную перезаливку peer'ов. Допустимы только точечные `wg|awg set <if> peer ...`.

Для остальных подключённых клиентов не меняются: ifindex интерфейса, сессия
(`latest-handshake` не сбрасывается внепланово), трафик идёт без потерь.
Проверяется интеграционным тестом (раздел 8.3).

## 7. Параметры AmneziaWG: правила валидации и генерации

Два уровня правил:
- **Валидация** — жёсткие правила. Нарушение → ошибка `3`. Применяются к сгенерированным значениям и к значениям, прочитанным из конфига, если krot их меняет.
- **Генерация** — политика krot: значения выбираются в «безопасных» диапазонах. Любое сгенерированное значение обязано проходить валидацию.

Генерация использует `crypto/rand`. В тестах — детерминированный источник с фиксированным seed.

### 7.1. Общие правила валидации (все `awg*`)

- V-01: все числовые параметры — `uint16`, кроме H1–H4 (`uint32`).
- V-02: `Jmin ≤ Jmax`.
- V-03: `Jmax ≤ MTU`.
- V-04: `148 + S1 ≤ MTU + 80` и `92 + S2 ≤ MTU + 80` (handshake-пакеты с префиксами помещаются в UDP-датаграмму при MTU интерфейса; 80 — накладные расходы WireGuard IPv6).
- V-05: если задан `I1`–`I5`, строка соответствует грамматике CPS: теги `<b 0x…>`, `<t>`, `<r N>`, `<rc N>`, `<rd N>`; `N ≤ 1000`; hex — чётной длины.

### 7.2. `awg` (1.x)

Валидация:
- V-10: `H1..H4` — одиночные числа в диапазоне `5..2147483647`, попарно различны.
- V-11: `S1 + 56 ≠ S2` (размеры Init `148+S1` и Response `92+S2` не совпадают).
- V-12: нет `S3`, `S4`, диапазонов H, ключей 3.x.

Генерация:
- `Jc ∈ [4, 12]`, `Jmin ∈ [64, 128]`, `Jmax ∈ [Jmin + 64, min(1024, MTU)]`.
- `S1 ∈ [15, 150]`, `S2 ∈ [15, 150]`; при `S1 + 56 = S2` — перегенерировать.
- `H1..H4` — случайные в `[5, 2147483647]`, попарно различны.
- `I1` — только если передан `--i1` (тогда версия 1.5).

### 7.3. `awg2` (2.0)

Валидация:
- V-20: каждый `Hn` — число или диапазон `a-b`, `5 ≤ a ≤ b ≤ 4294967295`.
- V-21: диапазоны `H1..H4` попарно не пересекаются (одиночное число = диапазон `a-a`).
- V-22: `S3`, `S4` присутствуют; ключей 3.x нет.

Генерация:
- `Jc`, `Jmin`, `Jmax`, `S1`, `S2` — как в 7.2.
- `S3 ∈ [15, 150]`, `S4 ∈ [0, 32]`.
- Политика krot: размеры `148+S1`, `92+S2`, `64+S3` попарно различны.
- `H1..H4`: четыре непересекающихся диапазона в `[5, 2147483647]`, ширина каждого — случайная в `[2^16, 2^22]`, между диапазонами зазор не меньше `2^16`, порядок H1..H4 по возрастанию не обязателен.

### 7.4. `awg3` (3.1)

krot всегда создаёт `awg3` с включёнными Header Protection, RandomTrailers и DisableCookies.

Валидация:
- V-30: `HeaderProtectionKey` задан, 32 байта (формат кодирования — как ожидает `awg`; фиксируется в задаче T0).
- V-31: при заданном `HeaderProtectionKey`: `S1..S4 ≥ 12`.
- V-32: при Header Protection `H1=1, H2=2, H3=3, H4=4` (режим совместимости, тип пакета скрыт HP).
- V-33: при `RandomTrailers = on`: `S1 = S2 = S3 = S4`. Правило V-11 и политика различия размеров из 7.3 для `awg3` **не применяются**.
- V-34: диапазоны таймингов `a-b` с `a ≤ b`, и выполняются соотношения:
  - `RekeyTimeout.max < RekeyAfterTime.min`;
  - `KeepaliveTimeout.max < RekeyAfterTime.min`;
  - `RekeyAfterTime.max < RejectAfterTime.min`;
  - `MaxHandshakeAttempts.min ≥ 1`.
- V-35: `ContentPaddingAddition` — диапазон `a-b`, `a ≤ b`, `b ≤ MTU - 80`.
- V-36: `RandomTrailers`, `DisableCookies` — только `on`/`off`.

Генерация:
- `Jc`, `Jmin`, `Jmax` — как в 7.2.
- `HeaderProtectionKey` — 32 случайных байта.
- `S1 = S2 = S3 = S4 = s`, `s ∈ [12, 64]`.
- `H1..H4 = 1, 2, 3, 4`.
- `ContentPaddingAddition = 0-b`, `b ∈ [16, 64]`.
- Тайминги — диапазоны вокруг стандартных значений WireGuard (в секундах):

  | Параметр | Стандарт WG | Генерация |
  |---|---|---|
  | `RekeyAfterTime` | 120 | `a ∈ [100,115]`, `b ∈ [125,140]` |
  | `RejectAfterTime` | 180 | `a ∈ [170,180]`, `b ∈ [185,200]` |
  | `RekeyTimeout` | 5 | `a ∈ [4,5]`, `b ∈ [6,8]` |
  | `KeepaliveTimeout` | 10 | `a ∈ [8,10]`, `b ∈ [11,15]` |
  | `MaxHandshakeAttempts` | 18 | `a ∈ [15,18]`, `b ∈ [19,22]` |

- `RandomTrailers = on`, `DisableCookies = on`.

### 7.5. Что попадает в клиентский конфиг

Все AWG-параметры `[Interface]` сервера копируются в клиентский конфиг без изменений
(включая `I1`, `HeaderProtectionKey`, тайминги).

## 8. Тестирование

### 8.1. Порядок

Для каждой задачи: тесты по ТЗ → убедиться, что они падают → код → тесты зелёные.
Каждый тест ссылается на пункт ТЗ в имени или комментарии (`// SPEC 7.3 V-21`).

### 8.2. Unit-тесты (`go test ./...`, без root)

- CLI: матрица 4.3 целиком — для каждого действия обязательные, допустимые и недопустимые флаги; ноль и два действия; коды выхода.
- Парсер и сериализатор конфигов:
  - round-trip: прочитать → записать без изменений → байт-в-байт тот же файл (golden-файлы, включая чужие конфиги с произвольными комментариями);
  - добавление, удаление, блокировка, разблокировка peer'ов на golden-файлах;
  - метаданные `krot:`.
- Валидаторы: на каждое правило V-xx — минимум один валидный и один невалидный случай, граничные значения.
- Генераторы (property-based): для каждого типа 10 000 генераций с разными seed — каждая проходит валидацию своего типа; отдельно проверить, что `awg2` никогда не выдаёт пересекающиеся H-диапазоны, а `awg` — `S1+56=S2`.
- Аллокатор адресов: IPv4 и IPv6, пропуск занятых, network/broadcast, адреса сервера, заблокированные клиенты, исчерпание подсети (/30, /126).
- Определение версии AWG (3.1, 3.2): по golden-выводам `awg --version` и по конфигам.
- CPS-грамматика `--i1`.
- QR: конфиг помещается / не помещается.
- Вывод таблиц и JSON — golden-файлы.
- Атомарная запись: при ошибке посередине оригинальный файл не изменён.

Внешние команды (`wg`, `awg`, `systemctl`, `ip`) вызываются через интерфейс-исполнитель,
который в unit-тестах подменяется фейком с записью вызовов. Unit-тесты проверяют, что
клиентские операции **не вызывают** ничего, кроме `wg|awg set ... peer ...` и `show`.

### 8.3. Интеграционные тесты (build tag `integration`, root)

Выполняются в отдельных network namespace, никогда не трогают сеть хоста.

- Полный цикл для каждого типа (`wg`, `awg`, `awg2`, `awg3`): create → add-client → поднять клиента в соседнем namespace из выданного конфига → ping через туннель → lock (трафик клиента прекращается) → unlock (трафик восстанавливается) → delete-client → delete.
- **Тест незаметности**: клиент A подключён, идёт непрерывный ping (интервал 0.1 с). Во время пинга выполняются 20 циклов add/lock/unlock/delete для клиентов B, C, D. Проверяется:
  - потерь у A нет;
  - ifindex интерфейса не изменился;
  - `latest-handshake` у A не сбросился внепланово;
  - конфиг на диске соответствует ожидаемому.
- IPv6: туннель с dual-stack, ping6 через туннель.
- Чужой конфиг (созданный вручную): list, list-client, add-client сохраняют чужие строки.
- Параллельный запуск: 10 одновременных `--add-client` — все 10 клиентов в конфиге, адреса уникальны.
- `awg*` в CI работают на `amneziawg-go` (userspace), собранном из исходников на закреплённом теге.

### 8.4. Smoke-тесты пакетов

В контейнерах всех ОС из 2.1: установка `.deb`/`.rpm` → `krot --version` → `krot --help` →
удаление пакета.

## 9. CI/CD (GitHub Actions)

### 9.1. `ci.yml` — на каждый push и pull request

1. `gofmt -l` (пусто), `go vet ./...`.
2. Unit-тесты с `-race`, отчёт о покрытии.
3. Интеграционные тесты на `ubuntu-latest` под `sudo` (модуль WireGuard есть на раннере; `amneziawg-go` и `amneziawg-tools` собираются из исходников на закреплённых тегах, результат кэшируется).
4. Сборка бинарей `linux/amd64`, `linux/arm64`.

### 9.2. `release.yml` — на тег `v*`

1. Всё из `ci.yml`.
2. Сборка статических бинарей; версия, коммит и дата — через `-ldflags`.
3. Пакеты `.deb` и `.rpm` (nfpm), бинарь в `/usr/bin/krot`.
4. Smoke-тесты пакетов (8.4) в матрице ОС.
5. GitHub Release: бинари, пакеты, `SHA256SUMS`.

Установка — только из пакетов или бинаря релиза с проверкой контрольной суммы.
Инструкции вида `curl … | bash` в документации не допускаются.

## 10. План работ

Каждая задача — отдельный коммит (или несколько), в порядке ТЗ → тесты → код.

| № | Задача |
|---|---|
| T0 | Каркас репозитория, `go.mod`, CI с `gofmt`/`vet`. Сбор golden-выводов `wg/awg --version`, проверка формата `HeaderProtectionKey` и таблицы версий (3.1) на реальных релизах |
| T1 | Разбор CLI и матрица флагов (4) |
| T2 | Парсер и сериализатор конфигов с round-trip (5.1, 5.3) |
| T3 | Атомарная запись и блокировка (5.4, 5.5) |
| T4 | Валидаторы AWG (7.1–7.4) |
| T5 | Генераторы AWG + property-тесты (7) |
| T6 | Аллокатор адресов IPv4/IPv6 (6.5) |
| T7 | Исполнитель внешних команд + фейк для тестов |
| T8 | `--create`, `--delete`, `--up`, `--down` |
| T9 | `--add-client` + клиентский конфиг + QR |
| T10 | `--delete-client`, `--lock-client`, `--unlock-client` |
| T11 | `--list`, `--list-client`, `--json` |
| T12 | Интеграционные тесты (8.3), включая тест незаметности |
| T13 | Пакеты, smoke-тесты, `release.yml` |
| T14 | `README.md`: установка, примеры, коды выхода |

## 11. Вне рамок

- NAT, forwarding, firewall, sysctl.
- Установка WireGuard / AmneziaWG.
- Хранение приватных ключей клиентов и повторная выдача их конфигов.
- Миграция туннеля между типами (`awg2` → `awg3`).
- Генерация сигнатур `I1`–`I5` (только приём готовой через `--i1`).
- Бэкапы конфигов.
